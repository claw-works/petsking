# 前端渲染方案对比 · pet-study

前一篇《三种驱动范式对比》研究的是「**下一个动画由谁决定**」（驱动内核）。
这一篇研究另一个维度：**同一个驱动内核，动画到底怎么画到屏幕上**（前端渲染）。

为隔离变量，这三个方案共用**同一个驱动内核**——首页那套「概率动画链」
（`render-core/chain.js`，从 `pet.js` 提炼的纯逻辑：掷骰 → 加权分类 → 选动作 → 到时再掷）。
内核只吐出「现在该播哪个动作、播多久」，**怎么渲染完全由各方案的 `render` 回调实现**。

美术素材全部来自三个原始仓库，直接复用（没有自己造）：

| 目录 | 渲染方式 | 美术来源 | 素材形态 |
|------|----------|----------|----------|
| `render-gif/` | `<img>` 换 src | whale-on-desk | 37 个 `.gif`（鲸鱼） |
| `render-spritesheet/` | canvas 切图逐帧 | dsh-desktop-pet | 1 张 `spritesheet.webp` |
| `render-pixel/` | canvas `fillRect` 逐格画 | dsh-pet-sprite | 字符网格 + 调色板（无位图） |

---

## 共享内核：ChainDriver

`render-core/chain.js` 与渲染无关，接口：

```js
new ChainDriver({
  idle, actions, categories, clicks,   // 各动作池
  weights: { idle, action },           // 顶层权重（category = 100 - idle - action）
  playMs(name),                        // 该动作播多久后接下一个
  render(name, meta),                  // ← 渲染回调，三方案各自实现
})
```

内核循环：`掷骰 rollKind → 选动作 → render(动作) → setTimeout(playMs) → 再掷骰`，
形成永不停止的动画链。点击时 `click()` 插播 clicks 池里的动作，播完回链。

三个方案的差别**只在 `render` 回调这一个函数里**。

---

## 一、GIF：`<img>` 换 src

**最朴素的方案**。GIF 文件自带循环和帧时序，前端什么都不用管，换 `src` 就换动画：

```js
render: (name) => { img.src = 'assets/' + name + '.gif'; }
```

- **优点**：实现极简；美术在 GIF 里，改动画不用碰代码；浏览器原生解码。
- **缺点**：帧时序封死在文件里，代码无法控制单帧；透明 GIF 只有 1-bit alpha（边缘有锯齿）；
  多状态 = 多文件（这里 37 个）；切回同名 GIF 不保证从头播。
- **适用**：状态数中等、美术由设计师产出 GIF、不需要精细帧控制。whale-on-desk 正是如此
  （宿主端定状态，浏览器端 `<img>` 显示，500ms 轮询换图）。

---

## 二、Sprite Sheet：canvas 切图逐帧

**一张大图，切格子逐帧播**（`render-spritesheet/sheet.js`，移植自 dsh-desktop-pet 的
PetContract + AnimationController）。精灵表布局固定：8 列 × 9 行，每格 192×208，
一行是一个状态，行内从左到右是连续帧，每帧有独立时长：

```js
// 第 index 帧在大图里的像素矩形
frameRect(state, index) → { x: i*192, y: rowIndex*208, w:192, h:208 }
// canvas 切出当前帧
ctx.drawImage(sheet, r.x, r.y, r.w, r.h, 0, 0, cw, ch)
// 按每帧自己的时长 setTimeout 推进
setTimeout(nextFrame, row.durations[frameIndex])
```

- **优点**：一次 HTTP 拿全部帧（一张图）；**时序在代码里显式控制**（可变速、可暂停、可跳帧）；
  真 alpha（WebP/PNG）；比逐个 GIF 省请求。
- **缺点**：需要按约定格式产出精灵表（帧尺寸/行序固定）；加一个动作要重排大图。
- **适用**：帧控制要求高、想省请求、有 sprite sheet 产线（如 `hatch-pet` 技能）。
  dsh-desktop-pet 用它在原生透明窗口里逐帧渲染。

> 注：这里用的是仓库自带的 `text` **测试**精灵表——每状态一块带标签的色块（占位美术），
> 重点在演示「切帧渲染」这条路，不是最终角色美术。

## 三、像素 canvas 手绘：`fillRect` 逐格画

**零位图素材**（`render-pixel/pet-art.js`，移植自 dsh-pet-sprite 的 pet-art.ts）。
宠物是 24×28 的字符网格 + 调色板，运行时用 canvas 一格一格画出来：

```js
// 美术 = 字符网格（'.'=透明，字母=调色板色）
const POKA_BASE = ['........oooooooo........', '......oohhhhhhhhoo......', ...]
const PAL = { o:'#4a4553', h:'#f6f7fc', ... }
// 逐格 fillRect
for (y) for (x) { ctx.fillStyle = PAL[rows[y][x]]; ctx.fillRect(x*sc, y*sc, sc, sc); }
```

「动作」是一组帧键的序列（走 = `WA/WB` 交替，跳 = `JP`），rAF 里按 tick 切帧。

- **优点**：**完全不依赖任何图片文件**，美术即代码（可 diff、可程序化生成/变色/换装）；
  体积极小；LLM 可直接生成新宠物（原库就是让模型吐字符网格造宠物）。
- **缺点**：手绘精度有限（这里 24×28）；复杂动画写起来累；每帧全量重绘。
- **适用**：像素风、需要程序化生成/热切换美术、极度轻量。dsh-pet-sprite 靠它实现
  「一句话描述 → 模型画一只新宠物」。三只内置宠物（波卡/橘丸/蓝噗）可在页面切换。

## 四、SVG 矢量骨骼：关节补间

**和前三种位图方案根本不同**（`render-svg/rig.js` + `pet-rig.js`）。宠物不是「一帧帧图片」，
而是一组矢量图形（`path`/`ellipse`），每个可动部件挂在一个**关节**上。动画不是切帧，
而是让关节的**角度/位移做缓动补间**（连续插值）：

```js
// 关节：{ el: <g>, cx, cy 旋转锚点 }；姿势 pose：给若干关节目标值
rig.tweenTo({ armR: { rot: -120 } }, 300)   // 右臂缓动到抬起 120 度
// rAF 每帧：lerp 当前值→目标值，写进 <g> 的 transform
// transform = translate(锚点) rotate(角) scale(缩放) translate(-锚点)
// 呼吸/摆动是叠加的周期函数，不打断主补间
rig.setLoop(ph => ({ body: { ty: Math.sin(ph*1.6)*2 } }))
```

动作即「关节目标 + 周期叠加」：挥手=转手臂、走路=四肢反相摆动、跳=腿压缩+整体上下、
睡觉=头低垂+慢呼吸。

- **优点**：**无限缩放不糊**（矢量）；体积极小；**真补间**（连续插值，不是离散帧，最顺滑）；
  可程序化换色/改造型；零位图素材。
- **缺点**：复杂/写实造型难（适合几何简约风）；关节绑定和姿势要手工调；帧极多的爆发动画不如位图直接。
- **适用**：几何/扁平风、需要缩放自适应、想要顺滑补间、程序化换肤。Live2D/Spine 是它的重量级
  商业版（骨骼 + 贴图变形），成本高得多；纯 SVG 骨骼是最轻的「矢量骨骼」路子。三种配色可切换。

## 五、Three.js 3D：真三维模型

**第五种载体，唯一的 3D**（`render-3d/pet3d.js`）。宠物是几何体（球/扁球）拼的 3D 模型，
有**实时光照、阴影、透视**，可自由旋转看各个角度。动画和 SVG 骨骼同思路——补间各关节的
`rotation/position/scale`，只是扩展到三维（每个通道 xyz 三轴）：

```js
// 关节 = THREE.Group（head/armL/armR/legL/legR/body/root）
pet.tweenTo({ armR: { rz: -1.2 } }, 300)   // 右臂绕 z 抬起（弧度）
// 每帧 lerp 当前→目标，写进 group 的 rotation/position/scale
// 周期叠加做呼吸/摆动；渲染器 render(scene, camera)
```

Three.js 经 **importmap 从 CDN 加载**（`<script type="importmap">` 指向 jsdelivr），
纯静态页面即可，无需打包工具。默认缓慢自转展示全身，可拖拽手动转视角。

- **优点**：真 3D 空间（可绕看、透视、光影层次）；补间顺滑；程序化换色/造型；表现力天花板最高
  （可加材质/粒子/后处理）。
- **缺点**：**依赖 Three.js（~1.3MB，需联网 CDN 或自托管）**；WebGL 有兼容/性能门槛；
  建模比 2D 麻烦；移动端耗电。
- **适用**：需要 3D 观感、绕视角、光影质感的场景。是表现力最强但也最重的方案。
  再往上就是 glTF 骨骼动画 / 物理引擎 / 后处理，成本继续陡增。

> 这里用基础几何体手搓了一只简约小生物（球身+球头+四肢），重点在演示「3D 渲染 + 关节补间」
> 这条路；真实项目通常导入美术做的 glTF 模型 + 骨骼动画。

## 横向对比

| 维度 | GIF | Sprite Sheet | 像素手绘 | SVG 矢量骨骼 | Three.js 3D |
|------|-----|--------------|----------|--------------|-------------|
| 渲染载体 | `<img>` | `<canvas>` drawImage | `<canvas>` fillRect | `<svg>` + transform | WebGL |
| 素材文件 | 每动作 1 个 gif | 1 张大图 | 无（代码内） | 无（代码内） | 无（几何体）＋Three 库 |
| HTTP 请求 | 多 | 1 | 0 | 0 | 1（~1.3MB 库） |
| 帧时序控制 | 封在文件里 | 代码显式控制 | 代码显式控制 | 补间（无「帧」概念） | 补间（无「帧」概念） |
| 透明度 | 1-bit（锯齿） | 真 alpha | 真 alpha | 矢量（无锯齿） | 3D（有光影） |
| 缩放 | 位图，放大糊 | 位图，放大糊 | 位图，放大糊 | 矢量，任意缩放不糊 | 3D，可绕视角 |
| 动画性质 | 离散帧 | 离散帧 | 离散帧 | 连续补间（最顺滑） | 连续补间（3D） |
| 改动画成本 | 换 gif 文件 | 重排精灵表 | 改字符网格 | 调关节姿势 | 调关节姿势 |
| 程序化生成 | 难 | 中 | 易（LLM 可生成） | 易（改数值/换色） | 中（几何/glTF） |
| 造型上限 | 高（看素材） | 高（看素材） | 低（像素手绘） | 中（几何简约） | 最高（3D+光影） |
| 依赖/体积 | 中~大 | 中 | 极小 | 极小 | 重（Three ~1.3MB+WebGL） |

**和首页 webm 方案的关系**：webm（VP9-alpha）是第四种载体——真 alpha、体积小、
帧时序封在文件里（类似 GIF 但质量高得多）。四种载体各有取舍，驱动内核可以完全一致。

## 运行

```sh
cd pet-study && python3 -m http.server 8799
```

- GIF：http://localhost:8799/render-gif/index.html
- Sprite Sheet：http://localhost:8799/render-spritesheet/index.html
- 像素手绘：http://localhost:8799/render-pixel/index.html
- SVG 矢量骨骼：http://localhost:8799/render-svg/index.html
- Three.js 3D：http://localhost:8799/render-3d/index.html（首次需联网拉 Three.js CDN）

各页面点击宠物触发点击回应；像素页可切三只宠物、SVG/3D 页可切三种配色；3D 页可拖拽转视角。左下角 HUD 显示概率链掷骰日志。
